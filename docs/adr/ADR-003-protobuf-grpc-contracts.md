# ADR-003: Protobuf and gRPC as authoritative contracts

**Status:** Accepted
**Date:** 2026-09-04
**Phase:** 0

## Context

Legion spans two languages. The Go control plane and the Rust data plane must
agree exactly on what a transaction, a feature, a signal and a decision are.
Any divergence between them is a silent correctness bug in a financial system.

The contracts also need to be versionable: reason codes, feature definitions
and policy structures will change while historical decisions must remain
interpretable.

## Decision

Protocol Buffers over gRPC are the authoritative service-to-service contracts.
The `.proto` files in `protocol/protobuf/` are the source of truth; every
language binding is generated from them.

No hand-written parallel JSON contract is created for an internal gRPC service.

Bindings are generated per language by whichever mechanism removes the need for
an external toolchain. Go bindings are generated by `buf` and **committed** to
`protocol/gen/go`, because otherwise a Go build would require `buf` and
`protoc` on PATH. Rust bindings are generated at build time by a Cargo build
script with a vendored `protoc`, and are **not** committed, because Cargo can
express the toolchain as an ordinary dependency and Go cannot. The invariant is
the same in both cases — a clone builds with only the language toolchain
installed — even though the mechanism differs.

One exception, deliberately scoped: the interface between the behavioural agent
and the language model uses JSON constrained by a JSON Schema. A model emits
tokens, not protobuf wire format. This is a *model output constraint*, not a
transport, and its output is validated and converted into a `RiskSignal` before
anything downstream sees it.

## Alternatives considered

**JSON over HTTP.** Universally understood and trivially debuggable. Rejected:
no schema enforcement without bolting one on, larger payloads and more parsing
cost inside an 80 ms budget, and no generated types — so the two languages
would agree by convention rather than by construction.

**Cap'n Proto or FlatBuffers.** Zero-copy deserialisation is genuinely
attractive for the hot path. Rejected for now because protobuf's cost has not
been measured to be a problem, and because the ecosystem — gRPC middleware,
tracing, tooling, familiarity in the target industry — is much stronger. If
benchmarks later show serialisation is a material share of the budget, that
measurement is what would justify revisiting this.

**Apache Avro.** Strong schema evolution story, but the ecosystem is oriented
towards streaming and batch rather than low-latency RPC.

**A shared library instead of a network boundary.** Rust compiled into Go via
cgo or FFI. Rejected in ADR-006's terms: it removes the serialisation cost but
couples deployment, complicates the build, and makes the boundary invisible.
It remains a real option if serialisation proves expensive.

## Trade-offs

- Protobuf is not human-readable on the wire; debugging needs tooling.
- A code generation step exists in the build. Go's generated code is committed
  and CI verifies it still matches the contracts; Rust's is produced on every
  build, so it cannot drift and there is nothing to verify.
- Protobuf's default semantics erase the difference between "absent" and "zero".
  This matters enormously for features, so `FeatureFreshness` carries that
  distinction explicitly rather than relying on field presence.
- gRPC deadlines and cancellation are a genuine advantage here, not incidental:
  the deadline model (ADR-009) depends on them.

## Consequences

- `buf lint` and `buf breaking` run in CI. A breaking change to a contract is a
  deliberate, visible act.
- Reason codes are append-only: numbers are never reused and meanings never
  redefined, because historical decisions are interpreted through them.
- Contracts describe the domain, not implementations. Internal structures are
  not exposed through the protocol.
- Packages are versioned (`v1`) so that a v2 can coexist during migration.

## Revisit if

Benchmarks show protobuf serialisation is a material fraction of the request
budget, or a third-party integration makes a JSON edge API necessary — which
would be an additional contract at the edge, not a replacement internally.
